# Instamart Customer Intelligence and Support Copilot

## Overview

A single-repository Customer Intelligence and Support Copilot for Swiggy Instamart, covering four connected Parts:

- **Part A** turns messy CSV exports into a trusted analytical database with 12,309 clean orders, 1,200 customers and 40 products, answering seven SQL business questions.
- **Part B** segments 1,175 customers into four named groups using K-means on RFM features, then predicts which customers are likely to lapse using a Random Forest with test F1 of 0.71.
- **Part C** triages 164 support tickets through a privacy-safe pipeline (PII redaction, input guardrails, retry logic, output validation) achieving 100% accuracy with the few-shot prompt.
- **Part D** builds a TF-IDF policy retrieval system (12/12 retrieval, 12/12 grounding) and a ReAct refund agent that processes seven scenarios with tools, checkpoints and graceful fallbacks.

All data is synthetic and fictional, generated by the supplied `generate_data.py`. All model calls use the supplied offline `mock_llm.py` (no API key, no network, no cost). All monetary values are in INR.

**Four-question analysis (181 words):**

This data covers 11,110 completed grocery and instant-commerce orders placed across six Indian metro cities between April and September 2025, with amounts ranging from INR 9.60 to INR 3,998.00. The distribution is heavily right-skewed (skewness 4.61) with a mean of INR 269.91 versus a median of INR 135.00, indicating most orders are small with a long tail of high-value purchases driven by electronics. Using the 1.5 times IQR rule, 897 orders above INR 645.30 are statistical outliers (none below the lower fence at -283.50); these are not errors but legitimate electronics and bulk purchases that naturally produce a heavy right tail. The correlation matrix shows all pairwise correlations are very weak: the largest in absolute value is order_amount with discount_pct at -0.095, suggesting a slight tendency for higher-value items to receive smaller percentage discounts, though this magnitude is far too small to infer a causal relationship. The second-largest correlation, order_amount with quantity at +0.087, is similarly negligible. Delivery time shows near-zero correlation with all variables. A correlation of this size does not establish causation; it reflects at most a minor statistical association in this particular dataset.

**Chosen K = 4.** K=4 has the highest silhouette score (0.526), a clear elbow in the inertia curve, and provides an actionable number of segments the business can design distinct campaigns around.

**Why inertia alone cannot pick K:** Inertia always decreases as K increases because more clusters always reduce within-cluster variance. K=8 has lower inertia than K=2 but this alone would always favour the maximum K, overfitting the data structure without improving business interpretability.

### Task 2: TF-IDF Retrieval

Query "refund policy late delivery": all three top results from refund_policy.txt.

**TF-IDF explanation:** TF (term frequency) measures how often a term appears in a chunk, giving higher weight to frequently mentioned terms. IDF (inverse document frequency) measures how rare a term is across all chunks, down-weighting common terms.

**Limitation:** TF-IDF is a bag-of-words model and cannot capture semantic meaning. Two phrasings with the same meaning but different words (e.g. "money back" vs "refund") will have low similarity because TF-IDF matches exact word tokens, not concepts.

### Task 9: ReAct vs Plan-and-Execute (224 words)

Our ReAct agent makes model calls incrementally: S1 (late, small refund) takes 5 calls, S5 (cancelled order) takes 3, and S6 (order not found) takes 2. A plan-and-execute design emits the full tool-call plan in one shot and replans only on error.

For S6 (NOT_FOUND), plan-and-execute would emit a 4-step plan (get_order, search_policy, calculate_refund, issue_refund) but replan after step 1 returns an error, costing 2 calls, matching ReAct. For S5 (cancelled), it replans after discovering the order is cancelled, also matching ReAct at 3 calls. For the happy-path S1, plan-and-execute could reduce from 5 to 2 calls (one plan, one confirmation), saving tokens.

However, the saving is small for short conversations and comes at the cost of more complex replanning logic. ReAct handles unexpected observations (NOT_FOUND, cancelled, above-limit refunds) naturally because each step reacts to the last observation, requiring no special replanning code.

For S7 (LOOP), ReAct reaches FALLBACK_MAX_ITERATIONS after 6 calls, each requesting the same tool. Plan-and-execute would detect the loop at replan time, potentially stopping sooner, but this edge case does not outweigh the simplicity benefit.

For this refund workflow I would choose ReAct. The conversations are short (2 to 5 calls), so token overhead is modest, and the ability to naturally handle any unexpected observation without replanning logic makes the system simpler, more robust, and easier to extend with new tools.

## Limitations and Next Steps

**Limitations:**
- The Premium flag in the retention list comes from whole-window RFM (including September), which overlaps the lapse-label period. Therefore the retention list is illustrative and not a leakage-free evaluation.
- TF-IDF retrieval cannot capture semantic similarity; paraphrased queries may miss relevant policy chunks.
- The mock LLM is deterministic and keyword-based; real-world model behaviour would differ in accuracy and failure modes.
- The lapse model uses a simple binary cutoff (any order in September = not lapsed); a survival-analysis approach would be more nuanced.
- No encoder, scaler or resampler saw test rows, no data from 2025-09-01 onwards entered the features, and segment labels from Task 3 were not used as features.

**Next steps:**
- Replace TF-IDF with a dense embedding model for semantic policy retrieval.
- Expand the refund agent with real-time database writes and notification hooks.
- Add a feedback loop where human corrections retrain the triage classifier.
- Build a proper train/validation/test split for the retention list using time-based holdout.
- Deploy the copilot behind an internal API with authentication and audit logging.
